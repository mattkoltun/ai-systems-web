Engineering field guide · 101 to implementation

How an agent
gets work done.

A model proposes the next step. A harness turns it into a controlled cycle of planning, tool use, observation, and verification. Workspaces and sandboxes give that cycle a place to run.

01 / Mental model

Six pieces, six responsibilities

The words overlap in everyday conversation. Their boundaries matter when you design the system.

Inference

Model / LLM

Produces text or structured tool requests from the context it receives. It predicts; it does not directly execute your code.

Capability

Tool

A callable operation with a name, input contract, implementation, and result. It can read data or change the world.

Protocol

MCP

One way to discover and call external tools, and access resources or prompts. The host still decides what is available and permitted.

Procedure

Skill

Reusable instructions and examples for a task. It shapes decisions; it is not the executor.

Runtime

Harness

The code that assembles context, runs the loop, dispatches tools, applies limits, stores state, and records what happened.

Behavior

Agent

The model working through a harness toward a goal, adjusting its next action from observations and feedback.

One sentence: the model chooses a possible next move; the harness decides whether, when, and how that move becomes an action.
02 / Execution environment

Where does the work actually run?

An agent can inspect a repository or run a command only when its tools have access to an execution environment. These four terms describe different parts of that environment.

Durable scope

Workspace

The project context: repositories, files, settings, and task history. It usually lasts longer than one agent run.

Execution boundary

Sandbox

A constrained place for a task to read files, run programs, or edit code. It can restrict filesystem, network, CPU, and other resources.

Runtime package

Container

One possible way to package the processes, filesystem, and dependencies used by a sandbox. A sandbox can use other isolation methods.

Command interface

Shell

A command interpreter, such as bash or zsh, that starts processes inside the environment. A shell is one tool surface, not the whole sandbox.

A common containment pattern
WorkspacePersistent project context
SandboxTask-level execution boundary
Container or VMPossible isolation implementation
Shell + processesCommands read and change mounted files

How the harness crosses the boundary

  1. Locate the workspace. Choose the repository and relevant task state.
  2. Prepare the sandbox. Mount or copy only the files and capabilities the task needs.
  3. Expose a tool. A shell or file tool gives the model a callable interface.
  4. Validate and dispatch. The harness checks the request, then executes it in the sandbox.
  5. Return an observation. Exit code, output, errors, and file changes inform the next turn.

The harness can live outside the sandbox while dispatching operations into it. The model service may run elsewhere entirely. The diagram shows a common pattern, not a required physical nesting of every component.

Keep the boundaries distinct: a workspace holds the work, a sandbox constrains execution, a container may implement that isolation, and a shell is a way to run commands inside it.
03 / Harness anatomy

What makes software a harness?

A chat box that forwards one prompt and displays one answer is an application. It becomes an agent harness when it manages the repeated model → action → observation cycle, with control over execution and stopping.

InputUser goalRequest, constraints, success criteria
→
Control planeHarness / runnerContext · loop · policy · state · verification
⇄
DecisionModelReasoning, text, proposed calls
Execution planeTool dispatcher → APIs / files / MCP serversActual side effects and observations live here
01

Goal & context builder

Turns the request, instructions, relevant history, and available tools into the next model input. It keeps evidence useful and context bounded.

02

Model adapter

Calls the model API and normalizes text, structured tool requests, usage, and errors into events the runner understands.

03

Runner / state machine

Owns the loop: ask, inspect output, execute allowed calls, append observations, repeat, or stop.

04

Tool registry & dispatcher

Advertises tool schemas, resolves names, validates arguments, invokes implementations, and returns structured results.

05

Policy & approval gate

Checks identity, scope, and side effects before execution. A model request never grants itself permission.

06

State & checkpoints

Stores messages, plan, tool outputs, and progress so the run can resume or hand work to a later session.

07

Verifier & stop rules

Checks completion against observable criteria. It also stops on budget, deadline, cancellation, or unrecoverable failure.

08

Tracing & recovery

Records decisions, calls, latency, and failures. Timeouts, retries, and idempotency rules keep failures contained.

These are responsibilities, not eight required services. A small harness can implement them in one process; a production system may split them across components.

04 / Agent deep dive

What makes an agent an agent?

An agent is a goal-directed system that can choose at least one next step from what it observes. The model supplies judgment; the harness supplies the loop, tools, state, and limits that turn that judgment into work.

Goal+Model+Harness+Tools+Feedback→ Agent behavior
The defining choice

It selects the next action from evidence.

After a log query, it may inspect a deployment, ask for clarification, or finish. That choice depends on the result. A fixed sequence of steps is a workflow; agent behavior begins where the next step can adapt.

The control boundary

Its autonomy has a scope.

The harness decides which tools exist, what they can access, how many turns may run, and which actions need approval. The agent can pursue the goal only inside those boundaries.

Agent input, state, and output

The event that starts a run is only part of its input. The app also supplies identity, context, and constraints.

Input envelope

What enters the run

  • Goal or question and the trigger source
  • Authenticated actor, tenant, and permissions
  • Relevant records, files, or conversation history
  • Tool schemas, budget, deadline, success checks
→
Working state

What evolves inside

  • Plan and current hypothesis
  • Model messages and tool observations
  • Pending approvals and checkpoints
  • Trace, cost, retries, and stop reason
→
Output envelope

What leaves the run

  • Answer or structured result
  • Evidence and actions actually taken
  • Status: complete, waiting, or partial
  • Trace ID and remaining uncertainty

What can start a run?

The trigger decides when the app creates the input envelope. The agent loop starts after that handoff.

01

User request

A chat message or button asks the agent to research, draft, or act.

02

Webhook or event

A ticket, commit, order, or alert arrives from another system.

03

Schedule

A timer starts a recurring report or health review.

04

Queue job

A worker picks up a durable task after the app accepts it.

05

State change

A new file, database row, or metric threshold creates work.

06

Human resume

An approval or clarification restarts a paused run from a checkpoint.

1TriggerApp creates the goal and context
2DecideModel proposes answer or call
3Gate & actHarness validates and executes
4ObserveTool result enters state
5CheckContinue, pause, or finish

Steps 2–5 repeat while the goal remains open and the run stays within its budget. The interactive trace shows each decision in detail.

Real-world agent patterns

Each example has a different trigger, tool set, output, and boundary.

01

Incident investigator

Trigger: latency alert. Tools: metrics, logs, deployments. Output: evidence-backed diagnosis and mitigation proposal. Gate: production rollback waits for approval.

02

Order support assistant

Trigger: new customer ticket. Tools: authorized order lookup and policy search. Output: reply draft. Gate: refunds and outbound messages are separate actions.

03

Coding agent

Trigger: assigned issue or failed CI. Tools: repository search, shell, tests, patch. Output: code diff and test evidence. Gate: writes stay in a sandbox and merge needs review.

04

Document intake agent

Trigger: uploaded contract or invoice. Tools: extraction, database lookup, validation. Output: structured fields and exceptions. Gate: uncertain or high-value records route to a person.

A small server-side example

A support agent reads order status and returns a draft. The webhook or app must verify the customer before calling this function.

Install in a separate backend project
npm install @openai/agents zod
# Set OPENAI_API_KEY in the server environment
agent.mjs · read-only demo data
import { Agent, run, tool } from '@openai/agents';
import { z } from 'zod';

const orders = new Map([
  ['c-7:A-1041', { status: 'shipped', eta: 'Tuesday' }]
]);

export async function handleTicket(ticket) {
  const customerId = ticket.verifiedCustomerId;
  if (!customerId) throw new Error('Unauthenticated');

  const lookupOrder = tool({
    name: 'lookup_order',
    description: 'Read the current status of an order',
    parameters: z.object({ orderId: z.string() }),
    execute: async ({ orderId }) =>
      JSON.stringify(
        orders.get(customerId + ':' + orderId) ??
        { error: 'Order not found' }
      )
  });

  const agent = new Agent({
    name: 'Order status assistant',
    instructions: 'Look up current status. Draft a concise reply. Never claim a refund or send a message.',
    tools: [lookupOrder],
    modelSettings: { toolChoice: 'required' }
  });

  const result = await run(agent, ticket.message, {
    maxTurns: 6,
    signal: AbortSignal.timeout(30_000)
  });
  return { ticketId: ticket.id, status: 'draft',
           reply: result.finalOutput };
}

Read the boundaries in the code

  1. Trigger adapter: a verified ticket enters handleTicket.
  2. Identity: the tool closes over the authenticated customer ID; the model cannot supply a different one.
  3. Tool: lookup_order is read-only and has a Zod input schema.
  4. Harness: run performs the model/tool loop with a six-turn cap.
  5. Output: the app receives a draft and decides whether to display, review, or send it.

The in-memory map keeps the example small. In production, query an authorized database in the tool, persist run state as needed, and handle retries and approval paths in the application.

    07 / Planning & development

    A plan is working state, not a script

    The goal tells the agent what success means. A plan selects a route, but each observation can change it. The harness keeps the plan visible and bounded while the model revises it.

    From request to next action

    1. 01
      Define the outcome

      “Find the likely cause of latency, cite evidence, and propose a safe mitigation.” Add what must not happen: no rollback without approval.

    2. 02
      Break it into checks

      Compare current latency to baseline, inspect error logs, correlate deploy timing, then verify the leading explanation.

    3. 03
      Choose the next observation

      Call the smallest read-only tool that reduces uncertainty. Start with metrics or logs before considering a write action.

    4. 04
      Revise from evidence

      If the logs contradict the deployment hypothesis, update the plan and investigate another cause. Do not follow stale steps blindly.

    5. 05
      Check the outcome

      Run a verification query, compare with the success criteria, and report what is known, unknown, and proposed.

    Which tool should run next?

    The logs show timeouts starting near a release. You want to know whether a deployment coincided with the spike. Pick a call and see how the harness treats it.

    Decision note

    09 / Reaching the goal

    How does the harness know when to stop?

    It cannot guarantee that the model is correct. It can require observable evidence, check hard limits, and make the outcome explicit.

    ✓

    Completed

    The result meets the task's acceptance checks. Example: latency is explained by two independent signals, and the proposed mitigation is clearly separated from action taken.

    ⏸

    Waiting

    A necessary write operation needs approval, or the user must choose between materially different paths. The run saves a checkpoint and resumes later.

    !

    Stopped with limits

    Time, step, cost, or retry budget is exhausted, or a tool fails. The agent reports partial findings and what remains unverified.

    Completion check for the incident

    • Has the agent identified the affected service and time window?
    • Is the explanation supported by logs, metrics, or release data rather than a guess?
    • Did it verify a plausible alternative or name the remaining uncertainty?
    • Are proposed actions separated from actions actually performed?
    • Did every side effect pass the policy and approval gate?
    10 / Harness blueprint

    Build the smallest useful harness

    Start with one goal, a few typed tools, and a loop you can inspect. Add persistence, approvals, and more autonomy only when the task needs them.

    Minimal runner · illustrative pseudocode
    async function run(goal, tools, limits) {
  const state = { goal, messages: [], steps: 0 };
  while (state.steps < limits.maxSteps) {
    const input = buildContext(state, tools.schemas);
    const reply = await model.generate(input);
    record(reply);

    if (reply.isFinal) {
      return verifyAgainstGoal(reply, state);
    }

    for (const call of reply.toolCalls) {
      const args = validate(call, tools.schemas);
      await authorizeOrPause(call, args, state);
      const result = await executeWithTimeout(call, args);
      state.messages.push(toolResult(call.id, result));
      record(result);
    }
    state.steps += 1;
  }
  return partialResult(state, "step budget reached");
}

    In a real implementation, handle model errors, missing tools, retries, cancellation, output checks, and checkpoint persistence explicitly.

    1

    Define the contract

    Specify the goal, allowed actions, acceptance checks, and what must be approved.

    2

    Choose the environment

    Map the workspace and decide whether tools need a sandbox, shell, or external service.

    3

    Implement read-only tools

    Give each tool a narrow schema, timeout, clear error shape, and bounded output.

    4

    Wire the runner

    Feed tool results back to the model and cap turns, time, and cost.

    5

    Add controlled writes

    Introduce authorization, approval, idempotency, and an audit trail before side effects.

    6

    Evaluate real tasks

    Test success and failure cases: wrong tool, malformed args, empty result, timeout, and premature “done.”

    Common failure → harness response

    FailureWhat the harness does
    Model invents a tool nameReject or return a structured “tool unavailable” result; never execute an unknown operation.
    Arguments fail the schemaValidate before dispatch and let the model correct the request, within the retry budget.
    External API times outRecord the error, retry only when safe, or report incomplete evidence.
    Model claims completion earlyRun acceptance checks and ask for more evidence or return an incomplete outcome.
